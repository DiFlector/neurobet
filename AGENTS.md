# AGENTS.md

# Neurobet (Нейроставки)

## 1. Название проекта

**Neurobet** — исследовательский сервис для прогнозирования спортивных событий и симуляции ставок с использованием машинного обучения, локальной LLM и данных о матчах и коэффициентах Fonbet.

Основная идея проекта — не просто предсказывать исход матча, а построить полный замкнутый pipeline, в котором система:

1. получает актуальные данные о спортивных событиях и коэффициентах;
2. сохраняет изменения во времени;
3. формирует признаки для конкретного вида спорта;
4. ML-модель рассчитывает вероятности и ожидаемую ценность вариантов ставок;
5. локальная LLM дополнительно анализирует контекст, новости и внешние источники;
6. результаты ML и LLM объединяются в структурированный verdict;
7. отдельный `bet-manager` проверяет возможность ставки;
8. ставка записывается в виртуальный банкролл;
9. после окончания матча система определяет фактический результат;
10. вся история используется для анализа и последующего обучения моделей.

На первом этапе Neurobet работает **только в режиме виртуальных ставок (simulation/paper betting)**. Реальные денежные ставки не являются частью базового pipeline.

---

## 2. Главные принципы проекта

### Разделение ответственности

Каждый компонент должен выполнять одну понятную задачу. ML-модель не должна самостоятельно изменять баланс, LLM не должна самостоятельно ставить ставку, а frontend не должен содержать бизнес-логику расчёта ставок.

### Data-first подход

Любое решение должно быть воспроизводимым по сохранённым данным. Для важных сущностей и событий необходимо хранить timestamps и версии полученных данных.

### Спорт-независимое ядро

Ядро Neurobet должно работать одинаково для разных видов спорта. Специфика футбола, хоккея, тенниса, баскетбола и других дисциплин должна находиться в отдельных sport-модулях.

### ML важнее LLM

LLM является дополнительным источником информации и контекстного анализа. Она не должна заменять статистическую модель и не должна иметь право самостоятельно обходить ограничения `bet-manager`.

### Строгие контракты

Обмен между сервисами выполняется через явно определённые схемы данных. Все решения ML/LLM, передаваемые дальше в pipeline, должны быть структурированы и валидироваться.

### Сначала симуляция

Ставочный движок должен поддерживать виртуальный баланс, журнал операций, settlement и статистику. Архитектура должна позволять позднее добавить другой executor, не переписывая ML и LLM.

## 5. Основные сервисы Neurobet

### `collector`

Собирает данные Fonbet.

Основная задача — регулярно получать состояние матчей, линии, коэффициенты и результаты. Интервал между запросами должен быть случайным в диапазоне **5–10 секунд**, а timestamp каждого получения необходимо сохранять.

Collector не должен заниматься машинным обучением или принятием решения о ставке.

### `event-processor`

Приводит сырые данные к внутреннему формату Neurobet.

Он отвечает за:

- нормализацию событий;
- сопоставление сущностей;
- обновление состояния матча;
- определение изменений линии;
- подготовку данных для sport-specific pipeline.

### `neural`

Числовая ML-система.

Она рассчитывает вероятности исходов, confidence, потенциальный value/edge и другие метрики, необходимые для принятия решения.

Модель должна обучаться на исторических данных и проходить backtesting.

### `llm`

Локальная LLM, запускаемая на пользовательском сервере.

Предполагается использование небольшой модели, способной работать в условиях ограниченных GPU-ресурсов, включая NVIDIA GTX 1050 Ti.

LLM не является главным предиктором. Она получает структурированный контекст и возвращает строго определённый JSON.

### `research`

Отдельный контур внешнего информационного поиска.

Он собирает найденные материалы о матчах, командах, игроках, травмах, составах, форме и других факторах, которые могут дополнить числовую модель.

Важны:

- URL источника;
- время публикации;
- время получения;
- источник;
- краткое содержание;
- оценка свежести;
- связь материала с конкретным матчем или участником.

### `bet-manager`

Центральный контроллер виртуальных ставок.

Он является единственным компонентом, который может зарегистрировать ставку в системе.

Перед созданием ставки он обязан проверить как минимум:

- существует ли матч;
- актуальна ли линия;
- не завершён ли матч;
- соответствует ли ставка доступным рынкам;
- достаточно ли виртуального баланса;
- не превышены ли лимиты риска;
- не существует ли дубликат ставки;
- не устарел ли ML/LLM verdict;
- соответствуют ли данные ожидаемой версии схемы.

ML и LLM могут только **рекомендовать** ставку. `bet-manager` принимает итоговое техническое решение о том, может ли она быть зарегистрирована.

### `backend`

Предоставляет API для frontend и внешних внутренних компонентов.

Не должен дублировать ML-логику.

### `frontend`

Web-интерфейс Neurobet.

Через него необходимо видеть:

- текущие и завершённые матчи;
- коэффициенты и их изменения;
- прогнозы ML;
- verdict LLM;
- решения `bet-manager`;
- виртуальный баланс;
- открытые ставки;
- закрытые ставки;
- PnL;
- ROI;
- статистику моделей;
- историю экспериментов.

## 6. Работа с несколькими видами спорта

Нельзя писать футбольную логику непосредственно в общем ядре, если она не является универсальной.

Каждый спорт должен иметь собственный adapter/module, например:

```text
sports/
├── common/
├── football/
├── basketball/
├── hockey/
└── tennis/
```

У каждого спорта могут существовать собственные:

- entities;
- события матча;
- игровые состояния;
- features;
- модели;
- market mappings;
- правила settlement;
- preprocessing;
- evaluation metrics.

При этом общие инфраструктурные компоненты должны оставаться едиными.

Пороги ставки вида спорта не живут в ядре. Числа лежат в конфиге этого спорта, правила читают их только когда `sport_code` совпадает. Обучение и дообучение того же спорта используют тот же конфиг. Форма бектеста подставляет эти числа как стандарт и позволяет изменить их на один прогон; лайв и обучение продолжают читать файл. Если replay не передал порог, он наследует конфигурацию спорта; общий override применяется к обоим рынкам, а override рынка имеет приоритет. Баланс, проверка дублей, свежести линии и схемы остаются общими.

Каркас разделов для каждого спорта — в [sports.md](sports.md). Теннис описан в [tennis.md](tennis.md): первый сет только наблюдение и вход в вердикт матча, со второго сета ставка разрешена, окна коэффициента и порог вероятности берутся из `sports/tennis/tennis.cfg`.

## 7. База данных

История — одна из центральных частей Neurobet.

Необходимо сохранять не только итоговый счёт, но и временное развитие матча и линии.

Как минимум должны существовать сущности для:

- sports;
- competitions;
- teams;
- players;
- matches;
- match participants;
- match state snapshots;
- odds/market snapshots;
- model predictions;
- LLM verdicts;
- research documents;
- bet requests;
- accepted bets;
- rejected bets;
- settlements;
- bankroll transactions;
- model versions;
- experiments;
- training datasets.

Для временных данных timestamps должны быть обязательны там, где это необходимо для восстановления состояния системы в прошлом.

Особенно важно не допускать data leakage при обучении: модель должна использовать только информацию, которая была доступна системе на соответствующий момент времени.

При работе с Neurobet агент должен сначала читать:

```text
AGENTS.md

02-ROADMAP.md
```

Перед любым обучением, переобучением или переводом модели в бой агент обязан прочитать раздел 9.1 и [`.agents/rules/model-release.md`](file:///srv/neurobet/.agents/rules/model-release.md).

После реализации значимого архитектурного решения документация должна быть обновлена.

Нельзя:

- смешивать frontend, backend, ML и betting business logic в одном сервисе;
- позволять LLM напрямую изменять bankroll;
- позволять LLM напрямую регистрировать ставки;
- обходить проверки `bet-manager`;
- обучать модель на информации, которая появилась после момента принятия решения;
- удалять исторические snapshots ради экономии места без специальной политики retention;
- завязывать общее ядро на один вид спорта;
- хранить критические verdicts только в логах;
- использовать неструктурированный текст между критическими сервисами вместо версионируемых JSON-схем;
- называть тег модели по алгоритму, дате или случайному хвосту. Версия назначается по [`.agents/rules/model-release.md`](file:///srv/neurobet/.agents/rules/model-release.md);
- ставить в бой две версии одной линии или переводить свежеобученную версию в `ACTIVE` сразу после обучения. У тенниса в бою две разные линии: матч и сеты.

## 9.1 Обучение моделей

Этот раздел обязателен перед `make train`, `make train-all`, `POST /api/models/train`, ручным запуском `python -m app.train` и перед promote.

### Зачем две модели

На каждый спорт обучаются две линии:

- `{sport}_logistic_regression` — простая планка. Она видит общий вес признаков и почти не запоминает отдельные матчи.
- `{sport}_gradient_boosting` — гибкий кандидат. Он умеет учитывать сочетания признаков и легче подстраивается под уже виденные ленты.

В бой на одну линию выходит одна модель со статусом `ACTIVE`. Вторая версия той же линии остаётся `SHADOW` и на баланс не ставит. У тенниса линии матча и сета ставят обе. Смысл второй линии — сравнение на одних и тех же матчах: Brier и результат ставок. Если бустинг не лучше регрессии, в бою остаётся регрессия. Если лучше и проходит тень, в бой переводится он, а регрессия становится следующей планкой.

Promote снимает прежние `ACTIVE` той же линии. У тенниса боевыми одновременно стоят назначенные линии матча и сета; прочие виды спорта держат одну `ACTIVE`. Обе линии обучают вместе, чтобы сравнение шло по одной истории. Одну линию запускают отдельно только когда правка касается именно её.

### Как обучать

Выборка строится только из реальных завершённых матчей с числовым id Fonbet. Синтетических матчей нет.

Признаки среза берутся только из наблюдений не позже этого среза. Ничья и равный счёт остаются без метки и в выборку не входят. Если котировки стороны нет, цена равна 0 и проверка перевеса на ней не выполняется. Числа травм, усталости и новостей попадают в срез только если запись создана не позже него. Упоминаемые ниже пороги 2% и два подтверждения относятся к прежним моделям и историческим настройкам, если конкретная конфигурация спорта не задаёт иное.

Повтор одного `source_event_id` в выборку не входит дважды: остаётся запись с большим числом снимков линии. Матч не входит, если токен победителя, официальный результат Fonbet и счёт называют разные стороны, если официальный результат помечен отказом, неявкой или статусом `RETIRED`, `VOID`, `CANCELLED`, и если у тенниса счёт сетов `1:0` или `0:1` без отказа. Срез не входит, если коэффициент стороны выше 100 или сумма обратных котировок вне `1.02…1.35`. Подряд идущие снимки с тем же счётом и теми же двусторонними ценами схлопываются до одного до сжатия ленты. Строка сета не входит, если `set_winners` не совпадает с закрытым счётом геймов этого сета. Снимки в базе при этом не удаляются. Счётчики отброшенных матчей и срезов пишутся в лог обучения.

Модель учится на срезах с реальной линией, потому что в лайве она считает вероятность на всей ленте. Для исторического алгоритма обучения длинная лента ограничивается 12 срезами. Проверку решений проводят по полной ленте с котировками соответствующего рынка и задержкой исполнения; обучающие и проверочные матчи разделяются целиком по времени доступности результата. Порог решения и число подтверждений читаются из конфигурации соответствующего спорта. В реестр пишется модель последнего обучающего окна. Новая версия получает статус `SHADOW` и текущую боевую не снимает. Имя версии назначается по [`.agents/rules/model-release.md`](file:///srv/neurobet/.agents/rules/model-release.md). Тестовый тег `test_{sport}_v1.0.0` в бой не переводят. Теннис v4 имеет отдельную спецификацию и контракт из 23 признаков в [NewModels.md](NewModels.md); её экспериментальное обучение ограничивает суммарное число строк матча и сета двенадцатью на матч, сохраняя полную ленту для оценки.

Команды:

- `make train` — теннис, обе линии, шаг версии `patch`.
- `make train-all` — все виды спорта, обе линии.
- Одна линия: `docker exec -i neurobet_neural python -m app.train --sport tennis --model gb --bump patch`. Значения `--model`: `lr`, `gb`, `all`. Значения `--bump`: `patch`, `minor`, `major`.
- Очередь: `POST /api/models/train` с полями `sport_code`, `model_type` (`lr`, `gb`, `gbdt`, `all`), `bump`, `hyperparameters`. Задание забирает `neural`.

Если обучение этой линии уже идёт, повторный запуск новую версию не создаёт.

`make backtest` обучающую версию не регистрирует. Это отдельная проверка на реальных матчах с тем же правилом двух срезов. Она заново обучает модель на фолдах и не является прогоном уже сохранённого checkpoint.

Исторический бэктест админки и MCP — другой контур. Он берёт последние завершённые матчи, прогоняет сохранённые `ACTIVE` и `SHADOW` модели по полной ленте и ставит фиксированную сумму на отдельный бумажный баланс. Записи в `bets`, `ledger_entries` и боевой банкролл не создаются. Если баланс падает ниже порога, счётчик банкротств увеличивается, баланс возвращается к начальному и прогон продолжается. Порядок запуска и поля отчёта описаны в [docs/historical-backtest.md](docs/historical-backtest.md).

Теннисная логика матча и сетов — одна модель линии. С `tennis_v2.1.0` она читает счёт из скобок и текущего гейма, линию своего рынка и прошлые матчи игроков, которые уже закончились к этому срезу. Неизвестный игрок остаётся на половине, а не на нуле. Вердикт матча собирается из уже закрытых сетов, включая те, по которым вердикт поставить не успели, и из открытых сетов. Если картина спорная, матч ждёт. Метка сета пишется, когда сет закрылся или когда известен итог матча. Срез уже решённого матча и уже закрытого сета в обучение не входит. `tennis_v1.0.0` сеты не считает. `tennis_v2.0.0` и `tennis_v2.0.1` остаются в реестре как прежние тени.

### Что делать после обучения

1. Прочитать итог прогона: число матчей, режим проверки (`walk_forward` или `holdout`), число решений (`decision_rows`), log loss, Brier и AUC. Если `decision_rows` равен 0, метрика посчитана по всей ленте, а не по ставкам. Такую версию в бой не переводить, пока на проверочных матчах нет подтверждающих срезов.
2. Перезапустить `neural`. До перезапуска новый файл тени не загружается и рядом с боевой моделью не считается.
3. Не вызывать promote сразу после обучения.
4. Дождаться завершённых матчей. Сравнивать только пары на одном матче: процент побед, Brier, контрфактический ROI и PSI. Бустинг сравнивают с боевой моделью и с регрессией на той же истории.
5. В `ACTIVE` переводить через promote, когда выполнены гейты из [`.agents/rules/model-release.md`](file:///srv/neurobet/.agents/rules/model-release.md): не меньше 7 дней в тени, не меньше 100 пар, PSI не выше 0.25, контрфактический ROI не отрицательный, Brier тени не хуже боевой больше чем на 0.02. `force` для обычного выпуска не используют.
6. После promote снова перезапустить `neural`. Прежняя боевая версия этого спорта становится `RETIRED`.

## 9.2 Журнал сторон моделей

Это статистика, не банкролл. Таблица `model_bet_journal` хранит сторону, которую модель подтвердила: боевую и теневую, в том числе когда денег нет и `bet-manager` ставку не регистрирует. Число требуемых подтверждений зависит от активной политики спорта и модели; не считать два среза универсальным правилом. В строке есть модель, версия, тень или бой, рынок (`match_winner` или `set_winner:N`), сторона, время, вероятность, коэффициент, честный коэффициент, перевес, EV, уверенность и короткий текст, почему сторона выбрана. Сумма ставки здесь всегда 0: деньги остаются в `bets` и `ledger_entries`.

Когда известен победитель сета или матча, строка получает `won`, `lost` или `void`. Наблюдение без подтверждённой стороны в журнал не попадает. Админка считает по этому журналу завершённые ставки, победы и процент побед каждой боевой и теневой модели. В счёт входит любой рынок, куда модель поставила сторону, включая сеты. Возвраты и незакрытые строки не входят.

Читать журнал можно только через `GET /api/model-bets` и MCP-инструмент `neurobet_list_model_bets`. Во фронтенде этой истории нет.

## 9.3 Контракт теннисной модели v4

`tennis_market_offset_boosting / tennis_v4.0.0` — одна SHADOW-запись с двумя market heads: матч и сет. Оба получают ровно упорядоченные 23 поля `SELECTED_TENNIS_FEATURES_V4` из `packages/features/src/features/selection.py`; последним идёт `market_is_set` (0 — матч, 1 — сет). Рыночные вероятности и изменения линии должны соответствовать рынку решения. Коэффициенты, timestamps, рынок, номер сета и quality metadata не входят в этот входной вектор. Старые checkpoint читают собственный сохранённый `feature_names`.

V4 обучается на XGBoost logit-offset с `base_margin`; validation, replay и live используют один и тот же расчёт вероятности. Совпадающие по времени матчи удаляются из обучающего префикса fold. Выпуск остаётся SHADOW до прохождения обычных release gates; регистрацию новой тени нельзя использовать для изменения назначения активной линии.

## 10. Критическая цепочка принятия решения

Основная логика Neurobet должна выглядеть концептуально так:

```text
Fonbet
   ↓
collector
   ↓
raw snapshots
   ↓
event-processor
   ↓
normalized match state
   ↓
┌──────────────────────┐
│                      │
↓                      ↓
neural               research
│                      │
│                  local LLM
│                      │
└──────────┬───────────┘
           ↓
      combined verdict
           ↓
      bet-manager
           ↓
    validation + risk
           ↓
    virtual bankroll
           ↓
       settlement
           ↓
       statistics
           ↓
   training / backtesting
```

Это центральный pipeline проекта.

---

## 11. Что является конечной целью Neurobet

Цель проекта — построить систему, которая способна на исторических данных и в режиме реального времени оценивать качество собственных прогнозов, симулировать ставки, измерять прибыльность стратегий и постепенно улучшать модели.

Главным результатом считается не количество сделанных прогнозов, а качество проверяемого эксперимента:

```text
prediction → decision → simulated bet → outcome → evaluation → learning
```

Neurobet должна позволять сравнивать различные стратегии, версии моделей и варианты использования LLM на одной исторической базе данных и в едином формате экспериментов.

## 12. Интеграция с Model Context Protocol (MCP)

В репозитории реализован полнофункциональный **MCP-сервер** (`packages/mcp-server`), предназначенный для взаимодействия AI-агентов (в таких IDE, как **Cursor** и **Antigravity**) с платформой Neurobet.

### Конфигурация подключения:

Конфигурации хранятся в `.cursor/mcp.json`, `.agents/mcp_config.json` и глобальном `~/.gemini/config/mcp_config.json`:

```json
{
  "mcpServers": {
    "neurobet": {
      "command": "python3",
      "args": [
        "-u",
        "/srv/neurobet/packages/mcp-server/src/neurobet_mcp/server.py"
      ],
      "env": {
        "NEUROBET_API_URL": "https://necrolich.ru/diflector/neurobet",
        "PYTHONPATH": "/srv/neurobet/packages/mcp-server/src"
      }
    }
  }
}
```

> **Важно:** Все запросы (включая метрики и таргеты Prometheus) идут через единую точку входа `NEUROBET_API_URL` благодаря встроенному backend-прокси (`/api/prometheus/query`, `/api/prometheus/targets`). Никаких локальных портов наружу не выставляется.

### Доступные группы инструментов MCP:

1. **Здоровье кластера и мониторинг**:
   - `neurobet_get_system_health`: агрегированный статус БД, Redis, планировщика, банкролла и активных моделей.
   - `neurobet_query_prometheus`: выполнение любых PromQL-запросов к временным рядам.
   - `neurobet_get_prometheus_targets`: проверка состояния всех 5 таргетов сбора метрик.
2. **Управление ML-моделями и Shadow Mode**:
   - `neurobet_list_models`, `neurobet_get_active_model`.
   - `neurobet_get_shadow_report`, `neurobet_register_shadow_model`, `neurobet_promote_model`, `neurobet_rollback_model`.
   - `neurobet_simulate_inference`: безопасная песочница симуляции инференса без сайд-эффектов.
3. **Тренировки и Эксперименты**:
   - `neurobet_trigger_training`, `neurobet_list_training_runs`.
   - `neurobet_list_experiments`, `neurobet_compare_experiments`.
4. **События линии Fonbet и Web Research**:
   - `neurobet_list_live_events`, `neurobet_get_event_timeline`, `neurobet_get_event_odds`.
   - `neurobet_get_predictions`, `neurobet_list_model_bets`, `neurobet_get_research_packet`.
   - `neurobet_list_model_bets`: журнал сторон моделей, включая тень и решения без денег. Это не банкролл.
   - `neurobet_trigger_backtest`, `neurobet_get_backtest_run`, `neurobet_list_backtest_runs`: исторический replay сохранённых моделей на отдельном бумажном балансе. Это не боевой банкролл и не `make backtest`.
5. **Виртуальный банкролл и ставки**:
   - `neurobet_get_bankroll_summary`: баланс, equity, заблокированная маржа, PnL, ROI.
   - `neurobet_list_virtual_bets`, `neurobet_list_bet_proposals`, `neurobet_sync_settlements`.
   - `neurobet_get_data_quality_report`, `neurobet_get_scheduler_stats`.
