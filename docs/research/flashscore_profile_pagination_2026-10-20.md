# Проверка пагинации Flashscore для теннисных профилей — 2026-10-20

## Найденная причина

Профиль Djokovic (`AZg49Et9`) показывает видимую `Show more matches`, но её обработчик вызывает устаревший feed `pr_2_167_AZg49Et9_1_en_1_s`. Chromium получил для него HTTP 200 и тело `0`, при этом кнопка осталась активной. Такое тело нельзя использовать как доказательство конца доступной истории.

Текущий профильный feed использует нумерацию с нуля и формат:

```text
https://global.flashscore.ninja/2/x/feed/pr_2_<country_id>_<player_id>_<page>_1_en_1
```

Например, страницы `0`, `1`, `2`, `38`, `39`, `40` и `41` Djokovic вернули разные непустые наборы матчей. Страница `42` вернула HTTP 200 с пустым телом. Публичная сторонняя справка также описывает формат `pr_2_..._<page>_1_en_1`; рабочий код подтверждён прямыми запросами к источнику, а не только этой справкой: [описание Flashscore player results feed](https://fe.tonywang.io/docs/flashscore/flashscore-player-results).

Запросы `fetch()` из страницы Flashscore блокируются CORS в части запусков. Загрузка переведена на `BrowserContext.request`, использующий тот же Chromium/proxy-маршрут и HTTP-заголовок `X-Fsign`, без CORS-ограничения страницы. Между feed-запросами выдерживается конфигурируемый минимум две секунды.

## Сверка счётчиков

Первый проход остановился после страниц 0–37, когда общий ID-счётчик достиг `allEventsCount=1,498`. Это случайно совпало с числом одиночных матчей Djokovic, но не означало, что общий feed исчерпан: оставшиеся страницы содержали парные события. Полный проход подтвердил 42 непустые страницы 0–41 и пустой HTTP 200 на странице 42: 1 677 уникальных ID, из них 1 498 одиночных и 179 парных. Старый критерий был некорректен, потому что сравнивал объявленный singles count с общим числом ID.

Импорты исходной контрольной выборки были выполнены версией `flashscore-tennis-player-v4`: она принимала один пустой/`0` ответ текущего paged feed как терминальный. В этой версии сравнение `allEventsCount` с общим числом ID также было семантически неверным: один считает singles, второй включает doubles. Поэтому старые результаты не дают достаточного доказательства стабильности terminal-ответа или полной выборки.

В `flashscore-tennis-player-v5` пустой/`0` ответ требует повторного запроса того же адреса и второго пустого HTTP 200. Если повтор возвращает данные, они разбираются как обычная страница; неустойчивый ответ оставляет импорт частичным. Архив сохраняет число проверок, статус и ошибку повторного запроса. Неподтверждённая пустая страница не принимается как checkpoint. В v6 дополнительно исправлено сравнение счётчика: advertised count проверяется против уникальных одиночных ID, общий ID-счётчик остаётся диагностическим.

`full_accessible` описывает только доступный через текущий feed диапазон, а не всю карьеру игрока. Страница, URL, номер страницы, IDs, время получения, HTTP-статус, terminal probe и результат разбора архивируются до использования. Таймаут, лимит страниц, ошибка сети, 403/429, неподдерживаемое тело или неустойчивый terminal probe оставляют профиль частичным.

## Что сделано в коде

- Извлечение кода страны из стороны игрока (`PX`/`CA` или `PY`/`CB`).
- Текущий zero-based feed URL и запрос через `BrowserContext.request`.
- Дедупликация матчей по стабильному Flashscore event ID при перекрытии страниц.
- Полный обход до terminal response; `allEventsCount` — только диагностическая сверка.
- Архивирование страниц, включая пустой terminal response и ошибки запроса.
- Версионируемые контрольные точки содержат архивный путь, хеш, ID и версию парсера. После перезапуска сохранённый префикс принимается только при непрерывной нумерации, проверенном содержимом и совпадении свежей первой страницы; иначе страницы загружаются заново.
- Общий слот источника освобождается после каждого feed-запроса. Обработка БД выполняется после освобождения слота.
- При обходе первой feed-страницы допускается совпадение ID с начальным feed: это корректное состояние, а не остановка пагинации. На следующих страницах отсутствие новых ID остаётся отдельной причиной неполноты.
- Повторная загрузка профиля выполняется одним Chromium-маршрутом; отдельная предварительная загрузка главной/профиля удалена. Запросы пагинации повторяются с ограниченным сетевым backoff.
- Исправлена ложная склейка матчей тех же соперников в соседние дни: архивный матч требует совпадения даты и места. Два разных Flashscore ID внутри одного импорта получают отдельные ключи фактов.
- Тесты формата URL, определения страны по стороне игрока и существующий профильный parser suite.

## Новый профиль и поиск игрока

Проверка DOM-поиска обнаружила, что актуальный Flashscore возвращает подсказки через JSON API, вызванный самой поисковой формой; ссылки `/player/` в DOM не появляются. Поиск переключён на перехват только ответа `s.livesport.services/api/v2/search/` в обычной Chromium-сессии и фильтрует его до сущностей Tennis/Player с валидным восьмисимвольным ID и совпадающим именем. Live-поиск `Ben Shelton` вернул профиль `QNuG0Gzb`, пол мужской. Одно имя остаётся кандидатом, а не подтверждённой личностью.

Профиль Ben Shelton был поставлен в существующую durable очередь и обработан тем же браузерным импортером: `history_scope=full_accessible`, `pagination_complete=true`, два пустых terminal-ответа, `allEventsCount=321` совпал с 321 уникальным одиночным ID, 13 архивных страниц/ответов. Распарсено 309 завершённых результатов; 197 строк исключено диагностикой, 49 повторов схлопнуто. В текущей проекции оказалось 305 уникальных матчей — часть встреч уже была в архиве из историй соперников. До подтверждения source identity не создано ни одного факта метрик игрока. Повторное планирование вернуло тот же завершённый job ID, а не создало новый импорт.

После проверки обнаружено, что прежний импортер мог связывать participant и писать метрики только по нормализованному имени. Новая логика разрешает такую запись лишь для владельца refresh-задания или для последней подтверждённой Flashscore identity на момент доступности результата. Неоднозначный профиль теперь можно полноценно загрузить и сохранить отдельно, не загрязняя метрики участника до ручного подтверждения. После подтверждения refresh использует архивный checkpoint этого же URL, чтобы построить метрики без повторной загрузки всей карьеры. По фактической БД до этого исправления существовали 7,865 legacy facts без соответствующей подтверждённой identity; их ретроспективная проверка/инвалидация остаётся отдельной задачей и не была выполнена этим импортом.

Во время первого полного v5 задания импорт Fritz остановился на странице 19 при оставшемся соединении advisory lock в idle transaction. Перезапуск Research освободил соединение; сохранённый прогресс остался доступен, и задание продолжилось с checkpoint. После этого профильная браузерная сессия выполняется в отдельном процессе с пятиминутным пределом, а advisory lock использует непулируемое соединение. Durable job завершился на третьей попытке. Повторный отдельный импорт Antonius (`5f24ca19-7a20-47bb-a624-2f70b3828109`) завершился за одну попытку: до и после для его 59 source IDs было 53 внешние записи и 173 наблюдения. Следовательно, повтор не добавил матчей или observation-версий. Успешное завершение также очищает ошибку предыдущей попытки; обе актуальные jobs имеют `completed` и пустой `last_error`.

В ходе проверки обнаружили и закрыли ещё один эксплуатационный дефект: завершённая job могла показывать сохранённый `PROFILE_TIMEOUT` от неудачной попытки. Теперь успешное завершение сбрасывает `last_error`.

## Сквозная проверка PBP — 2026-10-20

Ранее сборщик реконструировал match slug из сокращённых имён. Профильный HTML уже содержал точный URL, но он не сохранялся в observation. История доступна до последнего пустого ответа feed, хотя объявленный `allEventsCount` расходится с наблюдаемыми ID; это отражено как `source_terminal_empty_response_count_mismatch`.

Реальная страница матча показала маршрут вкладки `summary/point-by-point/set-N`, а не прежний реконструированный `/point-by-point/set-N`. Сборщик теперь открывает вкладку «Ход матча», ждёт появления вкладок сетов и использует их фактические ссылки. На странице Antonius M. — Pedrico-Kravtsov A. Первый документ выявил локализационный дефект: заголовки `1-й сет` и `Тай-брейк` были на русском, а часть Flashscore-разметки тай-брейка находится вне `matchHistoryRowWrapper`. Версия парсера `flashscore-point-history-v2` разбирает секции по реальным заголовкам, сохраняет числовые состояния тай-брейка и игнорирует итоговую строку с superscript-счётом вместо счёта гейма.
