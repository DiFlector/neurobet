# Проверка импорта истории профилей в PostgreSQL — 2026-10-25

## Подготовка участников и прогноз

Первичная проверка на реальном одиночном событии Fonbet `69246760` (Ламенс С — Жакмо Э, event UUID `8ea9609c-6b59-4649-9a9c-75034795d709`) подтвердила готовность обоих профилей, но событие уже было завершено, а исторический forecast snapshot не мог служить live end-to-end доказательством.

- Ламенс: `available`, источник `tennis_my_life`, полная история, 569 матчей, metrics version 6.
- Жакмо: `available`, источник `tennis_my_life`, полная история, 147 матчей, metrics version 2.
- Для обоих ответ содержит `sync_error=null`; материализованные метрики доступны 2026-10-25 около 05:39 UTC.

По уточнённому правилу формат матча не блокирует локальный прогноз по текущему счёту. Если формат неизвестен, baseline считает следующий розыгрыш, гейм и текущий сет, а вероятность победы в матче и score-path scenarios оставляет пустыми. Когда live-счёт показывает, что участник уже выиграл два сета, а источник всё ещё считает матч live, код причинно выводит best-of-5. В предположении best-of-3 по умолчанию система не работает.

End-to-end пройден на свежем реальном live-событии Fonbet `69293289` (Срират Т — Ватанабэ-эрикссон А, event UUID `b04cf3b2-cc39-4aec-a716-8d99e048f717`). `POST /api/tennis-history/prepare` вернул HTTP 200 и `ready=true` для обеих сторон; в forecast сохранены метрики внешней истории v2 и v1. У профиля A история полная и пригодная (`7` матчей), но cache status сообщает `stale/SOURCE_FRESHNESS_UNVERIFIED`; профиль B `available` (`4` матча). Это состояние сохранено как ограничение evidence.

`GET /api/events/{id}/forecasts/latest` вернул `forecast_available=true` с вероятностями `next_point_a=0.62`, `next_game_a=0.775863`, `current_set_a=0.065789`. `match_a` отсутствует при неизвестном best-of; `match_win_probability_reason=MATCH_FORMAT_UNKNOWN`. У обоих игроков отсутствуют пригодные serve logs, поэтому `data_quality=0.0`; прогноз доказывает прохождение расчётного пути и чтение внешних metric versions, но не является оценкой того, кто сильнее. Обученная модель победителя в этой проверке не использовалась. В live-источнике Fonbet также встречался эквивалент нуля `"00"`; parser теперь принимает его как love.

Collector, временно запущенный для свежего real-data прогона, после проверки остановлен.

Для этого прохода исправлены три узких дефекта: локальный forecast больше не блокируется неизвестным best-of и явно опускает match-win probability; legacy profile metrics без `source_player_id` читаются только после причинного подтверждения того же Flashscore ID и материализации после этого подтверждения; Fonbet-значение очков `00` нормализуется как love. Neural пересобран и перезапущен. Regression + PostgreSQL identity-as-of suite: **21 passed**.

## Идемпотентность и исправления на реальной БД

На реальном PostgreSQL через кодовый путь `persist_profile_facts` выполнена rollback-only транзакция для существующего участника из указанного выше события. Проверка использовала уникальный изолированный source match key и два временных подтверждённых source profile ID; транзакция принудительно откатилась, строки фактов отсутствуют, версия production-профиля восстановлена.

Проверенные результаты:

- Первый результат A создал одну append-only версию и поздний результат увеличил количество матчей профиля с 569 до 570.
- Повторный импорт A из того же профиля добавил 0 версий.
- Исправление A → B добавило версию, изменило history digest и пересчитало агрегат; уникальный матч остался посчитан ровно один раз.
- Исправление B → A добавило следующую версию и восстановило исходный digest A.
- Повтор A из второго подтверждённого профиля добавил 0 версий.
- Перед rollback metrics version прошла `6 → 7 → 8 → 9`; после rollback тестовых фактов осталось 0 и production metrics version снова равна 6.

Результат: поведение идемпотентного импорта, коррекции, межпрофильного повтора и пересчёта поздней коррекции подтверждено транзакционно на рабочей БД без постоянных тестовых записей.
